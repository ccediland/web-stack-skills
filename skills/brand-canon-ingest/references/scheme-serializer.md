# Scheme serializer — spine schemes to role-level CSS

Load when generating `schemes.css`, wiring dark mode or a register variant, or debugging scheme output.

## Why a serializer and not Style Dictionary

The scheme sets (`tokens/schemes/*.tokens.json`) stay in the spine's structured-OKLCH form — `$value` is an object (`colorSpace`/`components`/`alpha` plus a `hex` field), which SD v5 splits into `-value`/`-unit` sub-vars, and the brand repo pre-emits no string projection for them. The crossing is a ~50-line zero-dep serializer that byte-matches the brand's own canonical serialization (the C-1 pattern from its `tools/tokens-project.mjs`), so scheme values reconcile against the spine exactly like `tokens/web/` does.

## The vendored script

Save as `scripts/scheme-serialize.mjs` in the site repo and add it next to the SD hooks:

```json
"scripts": {
  "prebuild": "node build.mjs && node scripts/scheme-serialize.mjs ../furever-brand",
  "predev":   "node build.mjs && node scripts/scheme-serialize.mjs ../furever-brand"
}
```

```javascript
// scheme-serialize.mjs — vendored C-1 scheme serializer (zero-dep, Node >= 22)
// Reads <brand-repo>/tokens/schemes/*.tokens.json (structured-OKLCH spine) and emits
// src/styles/schemes.css: one block per scheme, role-level custom properties.
import { readFileSync, writeFileSync, mkdirSync } from 'node:fs';
import { join, dirname } from 'node:path';

const BRAND = process.argv[2];               // path to the brand repo checkout
const OUT = process.argv[3] ?? 'src/styles/schemes.css';
if (!BRAND) { console.error('usage: node scheme-serialize.mjs <brand-repo-path> [out.css]'); process.exit(1); }

const PREFIX = 'ds-scheme';                  // stays inside the stack's --ds-* namespace

// C-1 canonical serialization — byte-parity with the brand repo's tools/tokens-project.mjs
const canonNum = (n) => { const x = Number(n); return Number.isFinite(x) ? String(x) : String(n).trim(); };
const canonAlpha = (a) => (a == null || Number(a) === 1 ? '' : ` / ${canonNum(a)}`);
const serialize = (v) =>
  v != null && typeof v === 'object' && v.colorSpace && Array.isArray(v.components)
    ? `${String(v.colorSpace).toLowerCase()}(${v.components.map(canonNum).join(' ')}${canonAlpha(v.alpha)})`
    : String(v);                             // the `hex` field is ignored — no-fallback OKLCH policy

// Per-brand selector adapter. The canon names no stack: canon/canon.json > schemes declares each
// scheme's intent (default, mode, suggested class); the consumer maps it to real selectors. Fill
// this from that block. Object order IS emit order — the selectors tie on specificity, so source
// order decides the cascade: the :root default MUST come first or a dark block emitted before it
// silently wins on light pages.
const SELECTORS = {
  lightA: ':root',                           // default scheme — light, never auto-switched (G-UX-02)
  lightB: '.theme-lb',                       // opt-in variant classes as canon.json declares them
  darkA: '[data-theme="dark"]',              // the stack's dark seam (astro-css-tokens convention)
  darkB: '.theme-db',
};

let css = '/* GENERATED by scheme-serialize.mjs - do not edit. Source: <brand-repo>/tokens/schemes/ */\n';
for (const [id, sel] of Object.entries(SELECTORS)) {
  const file = join(BRAND, 'tokens', 'schemes', `${id}.tokens.json`);
  const tree = JSON.parse(readFileSync(file, 'utf8'));
  const roles = tree?.scheme?.[id]?.color;
  if (!roles) { console.error(`scheme-serialize: unexpected shape in ${file} (want scheme.${id}.color)`); process.exit(1); }
  const lines = Object.entries(roles)
    .filter(([k, t]) => !k.startsWith('$') && t && typeof t === 'object' && '$value' in t)
    .map(([role, t]) => `  --${PREFIX}-${role}: ${serialize(t.$value)};`);
  css += `\n${sel} {\n${lines.join('\n')}\n}\n`;
}
mkdirSync(dirname(OUT), { recursive: true });
writeFileSync(OUT, css);
console.log(`scheme-serialize: ${OUT} written (${Object.keys(SELECTORS).length} scheme blocks)`);
```

Output shape (excerpt):

```css
:root {
  --ds-scheme-bg: oklch(1 0 0);
  --ds-scheme-text: oklch(0.3436 0.0087 295.1);
  --ds-scheme-action: oklch(0.5996 0.0352 251.3);
  /* ... every role in the scheme, ~50 per block ... */
}
[data-theme="dark"] {
  --ds-scheme-bg: oklch(0.3436 0.0087 295.1);
  --ds-scheme-text: oklch(1 0 0);
  /* ... */
}
```

Because the overrides are role-level custom properties, a variant class also themes a SUBTREE: `.theme-lb` on one section re-inks just that section — useful when one register (e.g. a memorial block) lives inside a default-scheme page.

## Import order and the semantic bridge

Add `schemes.css` to the global stylesheet AFTER the token imports, then bridge the semantic-tier vars to their scheme-role counterparts once. The bridge is hand-authored (role vocabularies are brand-specific; map only true correspondences):

```css
/* src/styles/global.css */
@import 'tailwindcss';
@import './tokens.css';
@import './theme.css';
@import './schemes.css';
@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));

/* semantic bridge — re-point semantic vars at scheme roles so every Tailwind
   utility built on them becomes scheme-reactive. Furever mapping shown. */
:root {
  --ds-semantic-color-background: var(--ds-scheme-bg);
  --ds-semantic-color-foreground: var(--ds-scheme-text);
  --ds-semantic-color-action:     var(--ds-scheme-action);
  --ds-semantic-color-accent:     var(--ds-scheme-accent);
  --ds-semantic-color-focus:      var(--ds-scheme-focus);
  --ds-semantic-color-highlight:  var(--ds-scheme-highlight);
  --ds-semantic-color-attention:  var(--ds-scheme-attention);
}
```

The bridge block must come after the `tokens.css` import — same selector, later source wins. Roles with no semantic counterpart (state colors, `field-*`, `hero-*`) are used directly as `var(--ds-scheme-*)` in component CSS, or added to `theme.css`-style `@theme inline` entries if a utility is wanted.

## No-flash script — light default, never auto-switch

The brand rule (G-UX-02) makes light the default and forbids auto-switching, so the no-flash script defaults to `light` and ignores `prefers-color-scheme`. This deliberately replaces the astro-css-tokens reference script (which falls back to the OS preference):

```astro
<script is:inline>
  (function () {
    const stored = localStorage.getItem('theme');
    document.documentElement.setAttribute('data-theme', stored === 'dark' ? 'dark' : 'light');
  })();
</script>
```

Dark mode remains a user choice made on the site (a toggle writing `localStorage.theme`), never an OS inference.

## Verification

- `grep -c -- '--ds-scheme-' src/styles/schemes.css` — expect roles × schemes (e.g. 53 × 4 = 212).
- First block must be `:root`; toggle `data-theme="dark"` in devtools and confirm role vars flip.
- Spot-check one value against the brand repo's scheme file — serialized form must match the C-1 string (numbers normalized, no hex, alpha only when not 1).

## Limitations

- This document does NOT cover the token pipeline (astro-css-tokens) or which scheme a page should use (a design call the canon's grammar governs).
- The serializer handles color roles under `scheme.<id>.color`; other categories would pass through `String()` and need a deliberate extension.
